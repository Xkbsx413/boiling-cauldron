## P1：补生存模式获取入口（代码已实现，待构建测试）

### 问题

生姜、大蒜、贡菜、花椒目前存在生存模式获取死循环：

- 种子只能由对应作物合成（`ModRecipeProvider.java:49-67`）。
- 作物又必须用对应种子种植。
- 没有野生作物、草方块掉落、村庄箱子、流浪商人交易或其他初始来源。
- 因此新世界生存模式无法获得第一批种子，只能在创造模式或使用指令后开始种植。

其他材料已经有入口，不受此问题影响：

- 冬笋、竹荪可以通过竹根殖块繁殖获得。
- 盛花荷叶可以通过原版荷叶 + 花朵合成，再转化为藏藕泥块并获取莲藕。

### 目标

- 新世界生存模式不依赖创造模式、指令或其他模组，能够获得第一批生姜、大蒜、贡菜、花椒种子。
- 保留现有“作物 → 种子 → 扩大种植”的循环。
- 不破坏现有掉落表和合成配方。
- 获取方式应有明确提示，玩家不需要查源码猜测。

### 可选方案

1. **野外地物**
   - 在特定生物群系生成少量野生作物或种子。
   - 优点：沉浸感最好，探索有回报。
   - 缺点：需要 worldgen、生物群系标签和生成密度调优，工作量最大。

2. **草方块/蕨类掉落**
   - 破坏草或蕨时低概率掉落种子。
   - 优点：实现简单，玩家容易发现。
   - 缺点：四种作物都用同一种来源会缺乏区分度，且可能影响平衡。

3. **村庄箱子战利品**
   - 向不同村庄类型的箱子注入对应种子。
   - 优点：自然、低风险，容易通过数据包实现。
   - 缺点：依赖玩家找到村庄，且需要避免与其他模组的战利品表冲突。

4. **流浪商人交易**
   - 增加用绿宝石换种子的交易项。
   - 优点：稳定、可重复获取，适合作为保底来源。
   - 缺点：需要等待商人出现，前期节奏不可控。

5. **替代合成配方**
   - 用其他容易获得的材料合成首批种子。
   - 优点：实现最简单。
   - 缺点：容易显得突兀，需要合理设计材料。

6. **森罗厨房市场/交易整合**
   - 如果森罗厨房已有市场或交易系统，可以把种子接入其商品列表。
   - 优点：与前置模组联动自然。
   - 缺点：需要确认森罗厨房对应 API 和版本兼容性。

### 已确定方案（2026-10-30）

#### 全村民居保底

所有 5 种村庄民居箱子额外加入一个“调料包”奖池：

- 概率：8%。
- 数量：1 个随机种子。
- 权重：大蒜 30%、生姜 30%、贡菜 20%、花椒 20%。

这样即使玩家没有找到对应主题村庄，也有机会从任意村庄获得一种种子。

#### 流浪商人兜底

- 生姜种子：1 绿宝石换 1 个，库存 2。
- 大蒜种子：1 绿宝石换 1 个，库存 2。
- 贡菜种子：1 绿宝石换 1 个，库存 2。
- 花椒种子：1 绿宝石换 1 个，库存 2。

具体价格和库存可以在生存测试后调整。

## P2：实现钵钵鸡（待开始）

### 目标

实现第一条完整的成品玩法链：

1. 放置容器。
2. 放入冷水。
3. 放入一种底料。
4. 浸泡一段时间。
5. 用碗取出钵钵鸡。
6. 食用后获得与麻辣烫不同的效果。

### 当前状态

- 菌菇底料、麻辣底料、藤椒底料已经存在（`ModItems.java:22-24`），但目前只是普通物品，不可食用，也没有使用途径。
- 还没有钵钵鸡容器方块、BlockEntity、成品物品和食用效果。
- `docs/design.md:24-35` 已记录设计方向，但容器形态、容量、取餐方式、浸泡时长等仍未确定。

### 建议实现

#### 容器方块与 BlockEntity

- 新增钵钵鸡容器方块，例如 `bobo_chicken_pot`。
- 使用 BlockEntity 保存状态：
  - 底料类型（菌菇/麻辣/藤椒）。
  - 水量或是否已加水。
  - 浸泡进度。
  - 剩余份数。
  - 可选：是否已搅拌、是否需要清洗。
- 所有状态写入 NBT，保证区块卸载和重启后不丢失。

#### 交互流程

建议 MVP 流程：

1. 玩家放置容器。
2. 手持水桶右键加水，容器记录已加水。
3. 手持底料右键放入，消耗 1 个底料并记录类型。
4. 经过固定浸泡时间后进入可取出状态。
5. 手持碗右键取出一份成品，剩余份数减一。
6. 份数耗尽后容器保留，可清洗或重新加料。

需要明确的边界行为：

- 未加水时放入底料是否允许。
- 已放入底料后能否更换类型。
- 容器被破坏时内容物如何处理。
- 漏斗、发射器等自动化设备是否允许交互。
- 比较器是否输出浸泡进度或剩余份数。

#### 多人取用

- 容器不绑定玩家，任何玩家都可以取餐。
- 取餐时检查剩余份数，避免并发取餐导致负数或复制。
- 建议默认容量为 4 份，具体数值可在实现时调整。

#### 竹签

- 竹签可以作为后续扩展，不建议放入第一版 MVP。
- 如果后续加入，可用于串取特定食材或制作串串版本。
- 是否注册竹签物品仍保留为待定项。

#### 成品与效果

- 建议为三种底料分别提供三种钵钵鸡成品，便于配方、翻译和效果区分：
  - 菌菇钵钵鸡。
  - 麻辣钵钵鸡。
  - 藤椒钵钵鸡。
- 也可以使用一个物品加 NBT 区分，但独立物品更直观，也更适合后续扩展。
- 食用效果必须与未来的麻辣烫区分，具体效果待设计。

#### 表现

- 方块模型需要体现容器和内容物。
- 可以根据底料类型切换颜色或模型。
- 加水、放入底料、浸泡完成、取餐时播放对应音效和粒子。
- 取出后手持物品应有明确的名称和 tooltip。

### 实现范围

- 容器方块、BlockEntity 和 NBT。
- 加水、加底料、取餐交互。
- 浸泡计时和剩余份数。
- 三种钵钵鸡成品物品。
- 食用效果。
- 方块状态、模型、贴图、翻译、掉落表和创造模式物品栏。
- 容器合成配方。
- 多人、重载和破坏方块的边界测试。

### 验收标准

- 可以放置容器、加水、放入任意一种底料。
- 浸泡完成后可以用碗取出成品。
- 默认容量下可以取出多份，份数正确递减。
- 区块卸载、退出重进后状态仍然正确。
- 多名玩家可以正常取餐，不会复制物品。
- 三种底料对应成品和效果可区分。
- 容器破坏、空容器、未完成浸泡等边界行为明确且不会刷物品。
- 与麻辣烫的食用效果不重复。

### 风险

- BlockEntity 状态同步和 NBT 读写容易出错，需要重点测试重载。
- 取餐和破坏方块可能产生复制漏洞。
- 多人同时右键需要服务端权威判定。
- 容器模型和内容物渲染可能比预期复杂，可以先做简化版本。

## 与 P3 的关系

钵钵鸡和麻辣烫都应复用同一套“底料类型 + 汤底状态 + 份数”的数据模型：

- P2 先实现冷泡流程，不需要热源判定，范围更小。
- P3 再在此基础上增加热源检测、食材放入和热煮流程。
- 先完成 P2 可以验证容器、NBT、取餐和多人交互，为 P3 降低风险。
